### MEDIUM

**M1. A series' advance reminder can be set to a lead time that can never fire, and nothing previews it.**
`supabase/migrations/20261114090000_recurring_goals.sql:963-965` (create) and `:1042-1044` (update) accept `reminder_lead_days` 1–90 for every frequency. `apps/web/src/goals/schema.ts:240` and the form field (`goal-form-dialog.tsx:~486`) allow the same. `create_goal_period` (`:422-426`) copies the reminder into each new period and `schedule_goal_reminders` (`:555-556`) only queues moments still ahead. A period is created when it starts, so a lead time at least as long as the period is always in the past. Weekly with 7 or more days never reminds. Monthly with about 28 or more never reminds, and smaller leads can still miss when a period is created late.
_Verified:_ I created a personal weekly series with `leadDays = 10` and rolled it into next week. The period got an enabled `goal_reminders` row and **0** `job_outbox` rows. A monthly series with lead 1 queued one job, as expected.
_Impact:_ the person thinks they set a reminder, but it is silently never sent. Spec L134 requires "a preview of the next reminder date/time … including when a requested lead time has already passed". The series form shows no reminder preview at all.
_Remediation:_ cap lead days below the shortest period of the frequency in SQL, Zod and the form (for example weekly ≤ 6, monthly ≤ 27, yearly ≤ 90). Add the first period's reminder moment to the create preview (reuse `goal_moments_json`) so a passed moment is visible.

**M2. Some things the spec says must be visible are not shown in the interface.**

- **Create preview** (`goal-form-dialog.tsx:533-560`) shows the first and next periods plus a rules line. It does not show the timezone the boundaries use, and a Home series' timezone appears nowhere in the form. It also does not state what pause and stop do. Spec L103: "Make the recurrence schedule, start period, timezone, next instance and stop/pause behavior visible before enabling". The brief also says "a preview of the first and next periods **and the target**". The target is only in the form field above, not in the preview.
- **Series page** (`goal-series.tsx:108-149`, `CurrentPeriod`) shows no upcoming period and no timezone, although `get_goal_series` returns `nextPeriod` and `timeZone` (migration `:845-854`). Spec L110: "Display current, upcoming and historical periods clearly".
  _Verified:_ by reading the components. `nextPeriod` is used only inside the target dialog, and `timeZone` only to format history instants.
  _Remediation:_ in the preview, show the timezone (and for a Home series, say it is the Home's), the target and unit, and one sentence on pause and stop. On the series page, add a "Next period" line (when `nextPeriod` is not null) and the timezone.

**M3. The brief names tests that do not exist yet.**
`tests/db/rls/recurring-goals.test.sql` never calls `update_goal_series`, never tests a view-only member (`goal_settings.member_access = 'view'`) on a series or period, and never purges a series. The brief's test list names "permissions (member, **view-only**, …)". `update_goal_series` has the most untested logic in the migration (`:1063-1095`). It moves a personal series' unfinalized periods to the new timezone (rewriting `goals.time_zone` and `revision`), reschedules their reminders, enforces the end-date rule against the period running now in the new zone, and re-rolls.
_Verified:_ grep of the SQL test (no `update_goal_series`, no `'view'`, no purge). I probed by hand in a rolled-back transaction. A view-only member gets `not_permitted` for add, pause and target change, and sees `access = view`. A personal timezone edit returned `saved` and moved the running period to `America/New_York`. The behaviour is right; it is just not pinned by tests.
_Remediation:_ add DB cases for the series edit (title and reminder apply to later periods only; timezone moves unfinalized periods and not finalized ones; an end date before the running period gives `invalid_dates`; an end date reached auto-stops through `roll`). Add view-only member cases (no contribution, no Mark achieved on a completion period, no series changes). Add a purge that removes the periods and their entries.

### LOW

**L1. A Home timezone change leaves `next_roll_at` computed in the old zone** (`:475-484`). `sync_goal_periods(p_home_id)` only rolls series whose `next_roll_at <= now()` (`:527-528`). When a Home moves east, a period can count as ended for contributions (`goal_period_ended` uses the Home's current zone) while the new period is not created until the old `next_roll_at`, up to the offset difference later. The series page (`p_series_id` sync ignores `next_roll_at`) and the hourly job self-correct. _Remediation:_ recompute `next_roll_at` for a Home's series when its timezone changes, or have the context sync also roll series whose stored bound no longer matches today's.

**L2. The hourly rollover has no per-series isolation** (`:492-507`). Up to 200 series roll inside one RPC transaction. One series that raises an error (none found today, but a future constraint change could cause one) would abort the whole batch every hour. More than 200 series due at the same boundary drain at 200 per hour, so the remaining periods are created by lazy reads, and a short-lead reminder for a late-created period can be skipped. _Remediation:_ wrap each `roll_goal_series` call in a `begin … exception` block that logs and moves on. Document the drain rate in `docs/background-jobs.md`.

**L3. `change_goal_series_target` updates an archived current period** (`:1217-1258`). S30's `change_goal_target` refuses archived goals (`archived`). The series path changes the archived period's target and unit without that check. _Verified:_ by reading; nothing filters on `archived_at`. _Remediation:_ skip the goal update (or leave the series row only) when the current period is archived, and say so in the impact.

**L4. The Goals list read cost grows with history** (`:758-781`). Every list read computes `goal_status` and `goal_hidden` for **every** goal in the context, including all ended periods, then filters. Weekly series add about 52 rows per series per year forever. Fine at MVP scale, but it is linear in history. _Remediation:_ prefilter in the CTE (`series_id is null or archived_at is not null or period_end >= current_date - 1`) or add a partial index.

**L5. The target dialog can submit a different period than it displays** (`goal-series.tsx:418, 494-498`). When there is no `nextPeriod` and no current period (for example, the end date falls in the running period and the series was paused before it began), the initial `when` is `"current"`. That value is not among the options, so the select displays "A later period" while `effectiveFrom` is the current period's start. The server validates and the preview shows the date, so this is a confusion risk, not a data risk. _Remediation:_ derive the initial value from the options offered.

**L6. The target preview leaves out the reminders effect.** `impact.reminders` is returned (`:1235`) but `SeriesImpactSummary` (`goal-series.tsx:640`) does not render it. Spec L127 lists reminders among the preview items. _Remediation:_ add one line when the running period has reminders on.

## Explicit checks

- **Requirements (spec L2916–3019, done condition):** met for series kinds and frequencies (completion weekly refused in SQL, Zod and the form), period bounds, automatic idempotent creation without backfill, finalization reached / not reached with the next period at 0 and nothing carried over, manager-only historical corrections that recompute that period alone, mark it corrected and record `outcome_changed`, an achievement kept with needs-review instead of revoked, target from the current or a future period (next by default) with `confirm_status` / `confirm_unit` and stale-revision `conflict`, pause / resume / stop, and recurring reminders evaluated per period. Gaps: M1 and M2. The done-condition tests (month ends, February 2028 / 2032, year boundary at local midnight, weekly across New Year, duplicate job, two rollovers racing, correction racing rollover) exist and pass.
- **Cross-Home isolation and personal privacy:** `goal_series_for` / `goal_series_role` / `goal_series_lock` reuse S30 `goal_access` (membership plus capability). Personal series are owner-only. Lists filter by context. `sync_goal_periods` raises 42501 for a Home the caller is not in and silently returns 0 for a series they cannot see. Tests cover Home B and personal invisibility, and the periods of a trashed series are hidden through `goal_hidden` in `goal_for` / `goal_lock` / lists / notices.
- **Permissions:** creation, edit, state, target, delete and corrections of ended periods need `manage`. Contributors cannot add to or reverse their own entries in an ended period (`period_ended`), and a completion period's Mark achieved after the end needs `manage`. An Administrator without `manageHomeGoals` is refused (tested). Forged series ids and cursors give `not_found` / 22023. A period's target and deadline cannot be changed through the S30 functions (`series_period`, 22023). There is no role-escalation path. View-only behaviour is correct (probed) but untested (M3).
- **Secrets:** none added. The job uses the existing service-role client. `roll_goal_periods` is granted to `service_role` only (tested denied for `authenticated`).
- **Input validation:** Zod strict objects at every route (dates, frequency/kind refine, end ≥ first, reminder range, thousandths for target). SQL rechecks every field (`invalid series` / `invalid target` 22023) and table checks back the rules up (one owner, zone, completion-not-weekly, ends ≥ first, reminder pair, stopped pair, period columns). Gap: lead days are not checked against period length (M1).
- **Migration safety:** forward-only and additive. Constraints are widened with drop/add. S30 functions replaced with `create or replace` keep their grants, and the two wrapped S30 functions are renamed, moved to `private` and revoked (tested). The replaced functions keep S30 behaviour when `series_id` is null (compared line by line: `create_goal` / `archive_goal` limits only exclude periods, `update_goal` only adds the period guard, `add_goal_entry` / `update_goal_entry` / `set_goal_achievement` only add `period_ended` and the outcome recheck, which no-ops outside a series). Every new function is `security definer` with `set search_path = ''` and schema-qualified references. Lock order is series → goals throughout (roll, target, edit, restore). Period writes take only the goal lock and never the series lock afterwards, so there is no cycle, and the job's `skip locked` avoids waiting on readers. Idempotency rests on the unique `(series_id, period_start)` index including trashed rows, plus `on conflict do nothing` and a recheck under the series lock. Finalization is guarded by `finalized_at is null`. Boundaries are local dates via `goal_period_bounds`, so DST cannot move them. `goal_local_midnight` uses PostgreSQL's resolution for skipped midnights.
- **Test coverage:** strong for bounds, rollover, finalization, corrections, targets, reminders, trash/restore, the job and two concurrency races. Gaps are listed in M3.
- **Accessibility:** new sections use `aria-labelledby` headings, links have visible text, the preview is a `role="status"` region, needs-review is a `role="note"`, state is text (not colour only), dialogs reuse the shared accessible `Dialog`, and confirmations are labelled checkboxes. Component tests include axe (passing).
- **Performance:** the rollover batch is bounded (200 per run, 50 per context sync) and indexed on `next_roll_at`. Lazy sync costs one cheap RPC per list or series read. No N+1 from the client. The list read grows with period history (L4).
- **Maintainability:** the period rules are duplicated in SQL and `packages/domain` with cross-references, and the ADR documents the lock-order rule and known limits. Wrapping S30 functions by rename keeps the diff small but adds one layer to follow; acceptable.

## Remaining risks and test gaps

- Known limits the ADR accepts: a single period's page does not roll its series (finalization can lag up to an hour on that page); series history is capped at 50 events without paging; restoring a series from the trash does not recheck the 50-series limit.
- Untested paths: `update_goal_series`, view-only members on series, series purge (M3); Home timezone change mid-period (L1); a rollover backlog larger than one batch (L2).
- The Playwright spec (`tests/e2e/specs/recurring-goals.spec.ts`) was not run in this review. CI must run it.
- Spec acceptance items that depend on habit-to-goal links (linked series, source habit corrections) are out of scope per the brief (S30c).
- Achieved current periods are in neither Active nor Completed and live only on the series page (brief default 7). That is an owner decision against spec L99's "Completed section" wording.
