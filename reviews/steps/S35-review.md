# S35 independent review: photo libraries and processing

Branch `feat/photo-libraries` (uncommitted work, 49 files). Reviewer: fresh-context agent, read-only. Read: brief, ADR 0045, CLAUDE.md, Modules.md L114-160, the migration `20261121090000_photos.sql` in full, `tests/db/rls/photos.test.sql`, the finalize route diff, `photo-image.ts` and its test, the photo routes, `photos-view.tsx`, `photos-page.tsx`, the S15 `finalize_upload` / `expire_upload` / `trash_move` / `restore_file` / `purge_file_now` functions and the pets migration for comparison. I did not run the DB tests, the full suite or a build (CI does). The conclusions below come from reading the code, not from running it.

Verdict: PASS

No BLOCKER and no HIGH finding. 6 MEDIUM and 7 LOW findings. The MEDIUM items should be fixed or consciously accepted by the owner before merge; three of them (M1, M2, M3) touch the stated done-condition or the owner-approval gate.

Counts: BLOCKER 0, HIGH 0, MEDIUM 6, LOW 7.

## Findings

### MEDIUM

**M1. Upload rate limit makes batch import impractical.** `supabase/migrations/20261121090000_photos.sql:297-301` (`open_photo_upload`) reuses the S15 limits: 30 intents per account per hour across all purposes (`private.storage_limit('intents_per_hour')`, file_storage.sql:185) and 5 pending. The UI (`apps/web/src/components/photos/photos-view.tsx:146-175`) uploads a multi-file selection one at a time and keeps trying after the limit, so the 31st file in an hour and every file after it fails with "rate limited". Failed and abandoned intents also count. A photo gallery's normal first use (importing a trip) hits this. The error is truthful and safe, so this is not a defect in safety, but it is a product-level limit that the brief does not mention. Remediation: owner decision. Either a photo-specific hourly limit (for example 200) in `open_photo_upload`, or document the cap in the brief and UI help, and stop the loop on the first `rateLimited` failure instead of trying every remaining file.

**M2. Done-condition claims are only partly proven by tests.** `apps/web/src/photos/photo-image.test.ts`:

- "Keeps the first frame of a GIF" (line 128) uses a single-frame GIF produced by sharp, so it proves nothing about animation. No animated GIF or animated WebP fixture exists.
- HEIC orientation is not tested. Both fixtures are an unrotated 64x32 landscape (`fixtures/landscape.heic`, `with-exif.heic`). The code comment at photo-image.ts:136-138 says libheif applies `irot`/`imir` while decoding; that is plausible but unverified. iPhone portrait photos are the common case for this path, and orientation is named in the done-condition. JPEG orientation is tested for value 6 only (the 5/7/8 mirrored values are not).
- No test for a HEIC whose `ispe` claims more than the limits (only `heicClaimedSize` is tested; the refusal branch at photo-image.ts:128-131 is not).
- Corrupt-file coverage is good (truncated JPEG, truncated HEIC, bare header).
  Remediation: add an animated GIF (two frames, different sizes or colours) and assert the first frame; add a HEIC fixture with `irot` (a portrait phone-style file, or a hand-built rotation box test) and a mirrored-EXIF JPEG; add one oversized-`ispe` HEIC refusal test.

**M3. LGPL dependency and owner gate.** `apps/web/package.json` adds `heic-decode@2.1.0`, which pulls `libheif-js@1.23.5` (LGPL-3.0, verified in `node_modules`). The brief and ADR both say the owner must confirm this. CLAUDE.md requires no unapproved dependencies and owner decisions on open items. The PR must not merge before Ward answers; put the question first in the PR description. The fallback (refuse HEIC) is a one-line change in `private.upload_type_allowed` plus `schema.ts`, as stated.

**M4. HEIC decoding: memory/time exposure and a weak pre-decode guard.** `apps/web/src/photos/photo-image.ts:117-147`, `apps/web/src/app/api/v1/files/[fileId]/finalize/route.ts` (no `maxDuration`, nothing measured):

- `heicClaimedSize` takes the maximum of any `ispe` byte pattern. It is not tied to the primary item. A crafted file whose primary item is associated with a small `ispe` while its HEVC stream declares a large picture passes the check, and libheif allocates for the stream size before the post-decode `tooBig` check at line 128-ish can refuse it (libheif's own limits then apply, up to 32768 px per side, which is far above the 50 MP cap and could exhaust the wasm heap or the function memory). I could not run this; treat it as unverified but plausible.
- A 48-50 MP HEIC (an iPhone 48 MP photo is 8064x6048, just under the cap) costs roughly the RGBA decode (about 200 MB), a PNG intermediate, and four sequential sharp decodes of that PNG, all in a 1 GB free-tier function with the default duration. The ADR acknowledges this. The failure mode is a 500 or timeout that burns one of 3 finalize attempts (`finalize_attempts`) and holds the claim lease for 120 s.
- The finalize route imports `heic-decode` at module top level (photo-image.ts:5). `heic-decode/index.js` does `require('libheif-js/wasm-bundle')` immediately, so the wasm is instantiated on cold start of the finalize route for every purpose (avatars, attachments, covers).
  Remediation: lazy `await import("heic-decode")` inside the HEIC branch; export `maxDuration` on the finalize route; consider a lower HEIC pixel cap (for example 40 MP) or a documented measurement on the Vercel preview before release; decode the four variants from one decoded buffer without the PNG round trip if memory proves tight. Add the first real HEIC timing to the PR notes.

**M5. Every thumbnail is a no-store redirect, so nothing is cached.** `apps/web/src/app/api/v1/photos/[photoId]/content/route.ts:48-55` answers `Cache-Control: private, no-store` and a fresh 60-second signed URL for each request; the grid (`photos-view.tsx`, 60 `<img>` per page) therefore costs 60 session checks + 60 RPCs + 60 object fetches on every render, router refresh and album switch, with no browser reuse. Modules.md asks to avoid unnecessary repeated downloads. Per-request authorization is the right call for revocation, so a short private cache (for example `private, max-age=60` on the 302, consistent with the 60 s link life) would keep revocation within the documented download-URL window while removing most repeats. Owner/architect decision; at minimum record the trade-off.

**M6. No end-to-end proof that the four real objects' sizes drive the quota.** The DB tests use synthetic sizes (1000 per picture, `tests.variants`); the route test mocks `processPhoto` and `finalizePhoto`. Nothing runs real processed output through `finalize_photo`. The SQL logic is correct on reading (`finalize_photo` sums the four sizes and calls `finalize_upload`, which excludes the file's own reservation via `storage_usage(pool, file.id)`, and the file keeps that size through trash and restore), so I rate this a gap, not a defect. Also not covered: concurrent uploads near the limit (Modules.md acceptance criterion; the code relies on the pool lock taken in `open_photo_upload`/`finalize_photo`, which is correct but untested), finalize after the uploader lost Home membership (`finalize_photo` branch at migration:447-451), the `expired` finalize outcome, album limits (200 albums, 2000 per album) and the `album_limit` trash conflict, and `get_photo_upload_keys` for another user or a non-pending file. Remediation: add these DB cases; add one Vitest integration that processes a fixture and checks that the four reported sizes are what `finalizePhoto` receives; the E2E gap named in the brief should be tracked as a follow-up step.

### LOW

**L1. Migration header cites the wrong ADR.** `supabase/migrations/20261121090000_photos.sql:1` says "ADR 0043"; the ADR is 0045 (0043 is google-calendar-connect). Fix the comment.

**L2. Finalize doc comment not updated.** The block comment above `POST` in `apps/web/src/app/api/v1/files/[fileId]/finalize/route.ts` lists avatar, attachment, cover and pet purposes but not photos; it still says "The processed 512x512 WebP is stored". Add a paragraph for S35.

**L3. A lost Home membership returns a generic failure.** `finalize_photo` returns `invalid` when the uploader can no longer add to the Home (migration:447-451), and `finalizePhotoUpload` maps `invalid` to 500 `failed` (finalize/route.ts, the `default` case). The user sees "something went wrong" instead of "not permitted". Map `invalid` after a membership loss to 403 (needs a distinct outcome from the function), or accept and note.

**L4. Lock order differs from the S15 convention in `delete_photos`.** `delete_photos` locks the photo row first (`for update`) and then the pool (inside `trash_move`); `purge_file_now` and `finalize_photo` lock pool first. A concurrent delete and purge of the same photo, or two deletes of photos in different pools in opposite order, could deadlock; PostgreSQL aborts one with 40P01 and the client sees a 500. The pets module has the same pattern and the window is tiny. Optional: sort the batch by pool before locking, or retry once on 40P01.

**L5. Disclosure text is thinner than the spec asks.** `Photos.uploadHelp` says an optimized copy is kept, not the original. Modules.md also asks to disclose that original resolution and some metadata are not preserved, and to say plainly that downloads are the optimized version. The download link text is just "Download". Extend the help text and the download label ("Download optimized copy").

**L6. Storage figures are hidden from non-managers of a Home.** `photos-page.tsx` shows pool usage only where `getHomeStorageUsage` allows it (Home storage managers); other members see "storageHomeHidden". Modules.md says "show authorized members the applicable storage pool and its used, available and total capacity in Photos upload flows". This follows the S15 decision, but it should be a recorded owner choice, since uploaders are all members.

**L7. Accessibility and small UI points.** The per-file upload list (`photos-view.tsx`, `data-testid="upload-list"`) is not a live region; only the final summary is announced, so a screen-reader user does not hear individual failures as they happen. Thumbnails use `alt=""` with buttons labelled only "Open photo N" (acceptable without captions, but the viewer image has a generic alt). The "Add to album" select can show only the placeholder when none of the other albums are editable. Trash labels for photos are the English word "Photo" stored in the database (known, in the brief). The migration keeps adding rename-and-wrap trash functions (`*_before_photos`), which is now a long chain; fine for now, but worth a consolidation step later.

## Explicit checks

- **Requirements (Modules.md 4.7).** Personal and Home libraries, upload with optimized master plus three derivatives, original deleted, albums with multi-album membership, remove-from-album keeps the photo, seven-day trash with restore, quota accounting, 80/95 % warnings via the S15 pool, personal photos never visible to others: all implemented as specified. Wall-display, widgets, cross-Home sharing are correctly deferred to S36. Gaps: M1 (batch rate limit), L5, L6.
- **Cross-Home and cross-user isolation.** Good. Tables are RLS-enabled with every grant revoked (migration:176-178); every function is `security definer set search_path = ''`, rechecks `require_confirmed_caller()`, and scopes by `can_see_photo_library` / `photo_access` against current membership. Forged photo, album and Home ids return null/`not_found`/skipped, the same as nonexistent ones. `add_photos_to_album` only accepts photos of the album's own library. `get_photo_upload_keys` is limited to the caller's own pending photo upload. One tiny leak: `create_photo_album` with a client-chosen id that exists in another library answers `not_permitted` instead of `created`, which reveals that the UUID exists (negligible, random UUIDs).
- **Permissions.** Matches the brief's matrix. `finalize_photo` is service-role only (verified in the grants block; tested as denied for a signed-in user and anon). All other public functions: `authenticated` only. Private helpers (`%photo%` and the renamed trash hooks) are revoked from public/anon/authenticated. `manageHomePhotos` is added to `is_delegable_capability`, the engine and the capability labels consistently. Trash entries: visible to the deleter and photo managers only (tested). Display/child account special cases do not exist in the DB yet for any module (same as pets); S36 must add the wall-display authorization.
- **SECURITY DEFINER / search_path.** All new functions pin `search_path = ''` and use schema-qualified names; `pg_catalog` calls are qualified. No dynamic SQL except the grants loop with `%s` on `regprocedure`, which is safe.
- **Secrets / keys / SSRF.** Object keys are generated by the database (`gen_random_bytes(32)`), constrained by regex, and unique; the browser never chooses a key; the `variant` parameter is a zod enum; presigned links are GET-only, 60 s, type fixed. No outbound fetch of user-supplied URLs. No secrets logged (log helpers use short codes).
- **Input validation.** Zod strict objects at every route, size caps on bodies, UUID parsing for path ids, DB re-validates names (length, control characters, whitespace), batch sizes, offsets and types. Signature sniffing against the declared type, pixel and side caps, `failOn: "error"`, `limitInputPixels`, first frame only. CSRF: all mutations go through `readStorageMutation` (origin/JSON checks + verified identity); GET content route is idempotent and carries cookies same-site only.
- **Denial of service via decoding.** Mitigated for sharp formats (header check before decode, pixel limit, 25 MB cap, claim lease, 3 attempts). HEIC is the weak point (M4).
- **Migration safety and rollback.** Additive: four tables, functions, widened check constraints (drop/re-add on `audit_events`, `trash_entries`, `stored_files`, same pattern as pets/calendar; the constraint lists include every earlier value, verified against the calendar migration; the later Google calendar migrations add none). Rename-and-wrap of the trash hooks preserves earlier modules. Rollback is documented in the ADR as manual drop plus restoring constraints (database rollbacks are not automatic per CLAUDE.md). Apply-and-verify steps are in `docs/supabase-migrations.md`. The check-constraint rewrites scan the audit and stored-file tables once; acceptable at current size.
- **Quota accounting.** Verified by reading: the master is the file's own object; the three derivatives are tracked in `photo_variants`; `finalize_photo` finalizes the file with the sum of four sizes under the pool lock (`finalize_upload` excludes the file's own reservation, so a photo is never counted twice); the photo stays counted as `deleted` in the trash (`retire_file`), restore returns it to `ready` without a second charge (`restore_file`), multiple albums add no copies, purge sets `purged` and the trigger queues all three derivative objects plus the master (shared path), failed/expired/abandoned uploads queue all four. Pending uploads reserve the declared source size, which can be much larger than the final four-file size; that is conservative but may refuse an upload that would have fit after optimization (acceptable, mention in help text if desired).
- **Data-loss risks.** None found in the happy paths. If objects are written but finalize fails, the DB marks the file failed/expired and the trigger queues the derivative keys, and the route also deletes them. Retry after a partial put overwrites the same keys. A lost response after a successful finalize returns `ready` on retry (idempotent). Early purge and the seven-day purge delete the photo row and album memberships by cascade.
- **Test coverage.** DB tests are broad for isolation, quota, trash and albums (see M6 for gaps); route and component tests cover CSRF, validation, outcomes, delete confirmation and axe. Processing tests cover sniffing, HEIC decode, JPEG orientation, metadata stripping, mismatch and corruption (see M2). No E2E (flagged in the brief).
- **Accessibility.** Semantic nav/lists, labelled buttons and checkboxes, confirmation dialogs, status and alert regions, axe test passes in the component suite; see L7.
- **Performance.** Pagination (60), indexed library queries, per-row permission function calls are bounded; thumbnail redirect cost is M5; synchronous HEIC processing is M4.
- **Maintainability.** Follows S15/S31 patterns closely, with small focused modules; stale comments L1/L2.
- **Conformity with CLAUDE.md.** Supabase client only, no ORM, security-definer functions through `rpc`, validation at boundaries, €0 (R2 operations stay within free limits; no new service), owner approvals recorded in the brief/ADR, spec files untouched. Open item: the LGPL confirmation (M3).

## Remaining risks and test gaps

- HEIC memory/time on a free serverless function is unmeasured; a deployed-preview HEIC upload with a real 12 MP and a 48 MP phone photo should be tried before release.
- Colour management for HEIC: libheif output is treated as sRGB, so wide-gamut (Display P3) HEIC files may look slightly desaturated; JPEG sources are converted by sharp. Not specified by the brief; note for the owner.
- Concurrency (parallel uploads near the cap, parallel delete/purge) is untested; relies on the S15 pool lock.
- No E2E smoke for the photos page or an upload; the brief records this as a gap.
- Revocation of already-issued 60-second links cannot be immediate (architecture accepts this; the product copy for S36 sharing must say so).
- Reviewer did not execute the SQL or Vitest suites; the claims of passing tests in the brief were not independently reproduced.
