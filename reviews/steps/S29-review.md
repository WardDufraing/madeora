## Findings

### BLOCKER

None.

### HIGH

None.

### MEDIUM

**M1. A reused contribution id with a different quantity is answered `exists` (silent data loss).**
`supabase/migrations/20261112090000_numeric_habits.sql:752-760` (`add_habit_contribution`) treats any existing row with the same id, habit, contributor and date as an idempotent retry and returns `exists` without comparing `quantity`, `entered_unit` or `source`. The client makes this reachable: `apps/web/src/components/habits/habit-progress.tsx` (`ProgressEntry`, `attempt` state, about lines 150-190) keeps the same `attempt` id after a failed or lost request and does not regenerate it when the person edits the quantity. If the first request had in fact been applied (lost response), the corrected submit returns `exists`, `use-habit-contributions.ts:84` suppresses the toast, and the form clears as if the new amount were added. Impact: a person believes they added a different amount than the one recorded. Remediation: on retry compare the stored quantity (and entered unit); a mismatch answers `id_taken` (or a dedicated `id_reused`). Also regenerate the attempt id when the text or the entered unit changes.

**M2. A compatible-unit change does not carry the target or the presets over, although the spec requires it.**
Spec L2814 (line 22 of the confirmed unit block): when switching between compatible units, "convert the prospective target and increment settings transparently". `change_habit_tracking` computes `converted.target` and `converted.quickAdds` in the impact (migration lines 1206-1209) but the saved target is whatever the person typed. In `apps/web/src/habits/tracking-draft.ts:withUnit` and `habit-numeric-dialogs.tsx` (`TrackingChangeDialog`) the target text is left untouched on a unit change, so changing L to mL with "2" in the field saves 2 mL (the preview does show "from 2 L to 2 mL", but it is an easy trap), and the presets are reset to the new unit's suggestions rather than converted (the converted presets are never shown or applied; the dialog uses `withoutQuickAdds`). Remediation: when the new unit is convertible from the old one, prefill the target and presets from the exact conversion (via `convertThousandths`), and show the converted presets in the preview.

**M3. `change_habit_tracking` silently deletes every later scheduled version.**
Migration line 1249: `delete from private.habit_tracking where habit_id = ... and effective_on >= v_eff`. A target-only change "today" or "next" destroys a previously scheduled change (for example a unit change planned for next week), and neither the impact preview nor the event/audit details mention it (only the `unchanged` check at 1233 looks at later versions). Impact: an owner or manager loses a scheduled configuration without confirmation; the spec asks for explicit impact previews. Remediation: return the dropped versions in `impact` (for example `replacesLater`) and show them in the dialog, or refuse and require the person to cancel the later version first.

**M4. Rollback and migration-safety notes are missing.**
`docs/adr/0037-numeric-habits.md` (33 lines) and the `docs/supabase-migrations.md` addition have no rollback or backward-compatibility note. The migration moves seven public functions to `private` and re-creates them, drops the old `create_habit` signature (line 502) and adds a `derived` column. CLAUDE.md requires migration and rollback implications to be documented. Remediation: add a short section: expand-only data changes (new tables, one defaulted column), functions that have to be restored by re-applying the S28 migration, the old `create_habit` signature that clients still calling it with fewer arguments are covered by the defaults, and that data written to the new tables is not removed by a rollback.

### LOW

- L1. `add_habit_contribution` defaults `p_on` to the habit's today (line 751) inside the idempotency check. A retry that crosses local midnight sends `p_on = null`, resolves to the next date and answers `id_taken` for the person's own contribution. Remediation: have the client always send the explicit date it computed from `habit.today`.
- L2. Same function, lines 752-759: a contribution id that exists on another habit the caller can reach answers `id_taken`; this is an existence oracle only for random UUIDs and was judged acceptable. A PK violation (`23505`) from two concurrent calls with the same id on different habits surfaces as a 500; the habit lock does not serialize across habits. Very unlikely.
- L3. No cap on contributions per habit and day (or per member), so a member with `complete` access can grow `private.habit_contributions` and `get_habit_contributions` output without bound. The spec sets no limit and CLAUDE.md forbids inventing one, so this is an owner decision to record (a rate limit on the route would be the usual answer).
- L4. `changeTrackingSchema.expectedTotal` is capped at `HABIT_QUANTITY.max * 2` (`schema.ts`, about line 281), but a day's total is unbounded (many contributions of 1,000,000). Above 2,000,000 the preview request fails validation, and `TrackingChangeDialog.send` returns `null` without showing anything (`habit-numeric-dialogs.tsx`, `send`), so the dialog just does nothing. Remediation: drop the upper bound or show the validation error.
- L5. `blockNotScheduled` ("The habit is not scheduled today") is used for past days in the daily-totals rows (`use-numeric-texts.ts` mapping, `habit-daily-totals.tsx` is fed `day.block`). The English and Dutch text says "today". Use neutral wording ("on this day").
- L6. `ProgressEntry` on submit with a non-empty but invalid text sets `missing` but does not move focus to the field; the error text is shown and `aria-invalid` is set, but keyboard and screen-reader users get no focus move (`habit-progress.tsx` submit handler). Minor.
- L7. `HabitProgressWidgetBody` polls the full `GET /habits/:id` (includes `numericRecent`, trackings, schedules) every 60 seconds per widget. Acceptable now; consider a lighter summary read for widgets later.
- L8. `habitUnitInfo` (domain) validates the trimmed custom label but uses the untrimmed string as the dimension key, while the database stores exactly what is sent. The form trims before sending, so no mismatch results today; keep the API schema trimming in mind (`unitLabel` in `schema.ts` does not trim).
- L9. Manager corrections of another member's contribution write a history event and an audit entry (good), but the contributor is not notified. The spec says managers "must not silently rewrite" entries (L2881 area); the event list is the transparency mechanism. Confirm with the owner that this is enough for MVP.
