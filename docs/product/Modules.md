## How to use this document

The modules below describe user-facing feature boundaries, **not** separate security or data-ownership silos. The underlying account/Home/guardian/permission rules, Ora constraints, integration rules and acceptance criteria in `Project-specification.md` apply to every module. The MVP inventory in `Project-entry.md` also lists cross-cutting foundations F01–F04. All three previously approved development phases are intended for MVP, but the original per-phase checklist is missing; do not silently narrow the scope.

**MVP catalogue:** M01 Dashboard & widgets · M02 Calendar & scheduling · M03 Tasks & chores · M04 Shopping lists · M05 Recipes · M06 Meal planner · M07 Habits & routines · M08 Goals · M09 Rewards & points · M10 Pets · M11 Photos · M12 Ora · M13 Household Display · M14 Integrations. M12–M14 have their detailed primary requirements in `Project-specification.md` (§5, §6, §4.8–4.9 catalogue respectively). **Google Calendar is explicitly committed for MVP**; other integrations require verification.

## Detailed functional module descriptions (preserved)

## 4. Functional modules

### 4.1 Dashboard
- Personal and Home dashboards with user-configurable widget arrangements.
- Add, remove, rearrange, resize (where supported), and hide widgets.
- Flexible widgets, custom widget configurations, and curated/shared dashboard templates.
- Dedicated edit mode; normal dashboard use must not accidentally trigger layout edits.
- Personal templates and controlled Home template sharing; only authorized members may apply shared configurations.
- Contextual highlights and relevant suggestions, without overwhelming the interface.
- Useful empty states, including when a module is disabled or no data exists.

### 4.2 Calendar and schedule
- Native events and daily/weekly planning.
- Clear ownership/participants and personal vs Home visibility.
- Upcoming events widget and actionable day overview.
- **Google Calendar integration is required in the MVP** and is a core part of the calendar experience, not merely an optional future feature.
- On authorized connection, automatically retrieve events from selected Google calendars and keep them synchronized, including external changes.
- Creating an event in Madeora must create the corresponding Google Calendar event in the configured target calendar; edits must synchronize in supported directions. Deletion behavior is governed by the approved two-choice policy below. Recurring-event scope is confirmed below; synchronization failure details require further specification. Conflict resolution is defined below.
- Each user chooses which connected Google calendars appear in their personal dashboard and which are visible to each of their Homes; a user may belong to multiple Homes.
- When a user explicitly shares a calendar with a Home, the shared view can display the **full event title/details**, not merely a generic busy marker, subject to the user's selections and provider permissions.
- **Unshared events are entirely invisible to other Home members, including their times and busy/availability status.** No implicit availability sharing; enforce across all widgets, Ora, wall displays, notifications, search and APIs.
- Never silently expose calendars to a Home merely because an account was connected. External failures cannot corrupt or conceal native Madeora events.
- Calendar imports with preview, validation, and cautious duplicate handling.
- **Confirmed synchronization conflict policy: detect and request user resolution.** When both Madeora and Google Calendar have changed the same event since the last successful sync, do not silently overwrite either change or apply a blanket latest-write-wins policy.
- Preserve both conflicting versions and their provenance until an authorized user reviews the differences and chooses the intended result. Show an understandable conflict state and allow the user to resolve it; do not claim the event is fully synchronized while unresolved.
- Synchronize non-conflicting changes automatically. Avoid duplicate events and repeated conflict prompts; record the selected resolution and retry safely if a provider operation fails.
- Conflict prompts must respect the event's privacy, Home membership, and editing permissions. A Home member must never see a private version merely because a conflict exists.
- **Confirmed calendar deletion policy (option B, 12 October 2026):** For a Google-linked event deleted from Madeora, present a clear choice **“Remove from Madeora”** or **“Delete everywhere”** before acting. Explain the impact and affected Google calendar; do not silently delete from Google.
- **Remove from Madeora:** remove the event from the user's Madeora views without deleting the Google event. Preserve an explicit exclusion/hidden-event record so subsequent Google synchronization does **not** re-import and redisplay the event unexpectedly. This does not revoke access to the Google calendar or affect other events. Offer a way to restore a hidden event.
- **Delete everywhere:** after explicit confirmation, delete the linked event in Madeora and issue a deletion to the connected Google Calendar, subject to Google permissions and provider capabilities. Never claim deletion everywhere until the provider confirms it. If Google deletion fails or is unauthorized, show a partial-failure state with a safe retry or alternative; do not silently fall back to local-only removal.
- Only an authorized user may perform a deletion affecting a shared Home or Google calendar. Respect private event boundaries in all confirmations, audit information, and notifications. Recurring-event scope is confirmed below; events shared across Homes and recovery windows need separate product decisions.
- **Confirmed recurring-event policy (option C, 12 October 2026):** When editing or deleting a recurring event, offer three explicit scopes: **“This event”**, **“This and following events”**, and **“All events”**. Clearly show which occurrences will be affected before committing the change.
- For Google-linked recurring events, apply the chosen scope consistently across Madeora and Google Calendar, subject to the separately approved deletion destination choice (**“Remove from Madeora”** versus **“Delete everywhere”**). Never infer that a recurrence-scope choice also authorizes deletion from Google.
- Editing a single occurrence must preserve the rest of the series. Editing this and following occurrences must preserve historical occurrences. Editing all must affect the intended series. Where a provider cannot represent a requested change safely, report the limitation and do not claim successful synchronization.
- Recurrence exceptions, timezone/DST changes, concurrent edits, series splits, and partial synchronization failures must have explicit handling and acceptance tests. Preserve the confirmed ask-to-resolve conflict policy and privacy boundaries.

- Detailed calendar specification must define field-level versus event-level conflict detection, recurrence exceptions, concurrent deletions, offline edits, provider version tokens, and notification/recovery flows; these are implementation questions, **not** permission to replace the approved ask-to-resolve policy.


### 4.3 Tasks and chores
- Personal tasks, shared Home tasks, completion status, and relevant scheduling/assignment.
- Household chores with ownership and progress visibility.
- Dashboard actions should open or update the underlying records, respecting permissions.
- Task/chores can inform routines, rewards, and Ora summaries where appropriate.

### 4.4 Meals, recipes, and shopping
- Meal planning and recipe organization.
- Shared shopping lists with easy add/check-off flows.
- Practical links between planned meals, recipes, and shopping needs.
- Recipe and shopping-list imports with review, validation, and duplicate prevention.

### 4.5 Habits, goals, and rewards
- Track habits and goals over time, with useful progress views.
- Rewards and motivational feedback designed to encourage, not pressure.
- Rewards and points are **included in the MVP** for both personal and Home contexts.
- A configurable, fun Home leaderboard/points widget can show members' points.
- Exact scoring rules and eligible actions need a supporting specification; do not assume every completed task awards points.
- Avoid making reward mechanics mandatory for all households.

### 4.6 Pets
- **Dedicated pet profiles are owned by a Home, not by an individual.** Authorized Home members can add and edit pet information.
- Pet-related tasks and reminders are displayed in a **separate, configurable Home dashboard widget**, not buried in the pet profile.
- Pet profiles and their tasks follow Home-level access controls.
- Relevant pet reminders and widgets; Home permissions apply.

### Confirmed pet profile scope and optional fields (13 October 2026)
- **Approved option B, with explicit optionality:** Each Home-owned pet profile supports comprehensive everyday care information, but **not every field is mandatory**. Keep initial creation lightweight; require only a pet name and a valid owning Home (the Home is established by context). All other details may be added or edited later, including a photo, species, breed, birth date or approximate age, weight, veterinarian contact, allergies, medications, diet, identification details, general notes, and care instructions.
- Permit genuinely unknown, not-applicable, and not-yet-entered values. Do not fabricate a birthday from an approximate age, assume a medical status from an empty field, or require sensitive care details merely to create a profile. Validate provided values (e.g., dates, numeric weights and units, contact fields) without forcing optional fields to be populated.
- Support pet-linked medical history entries and appointments as an everyday reference, subject to explicit member input and existing module capabilities. Keep detailed health analytics, automated vaccination/treatment regimes, and extensive clinical record management outside this approved profile scope unless separately decided.
- Preserve the previously approved separate Home dashboard pet-task/reminder widget. Do not move tasks into the profile or automatically generate care tasks from optional medical fields. Respect Home permissions, record visibility, privacy, deletion/recovery, and audit rules for edits and linked entries.
- Acceptance criteria: create a pet with only its name in a Home; save and revisit a partially filled profile; add/remove optional fields; distinguish unknown from an explicitly recorded value; reject malformed entered data without blocking other optional omissions; view linked appointments/history when permitted; deny unauthorized edits; display pet tasks in the separate widget.

### Confirmed structured pet medical history (13 October 2026)
- **Approved option B:** Each Home-owned pet may have a chronological, structured medical history covering veterinary visits, vaccinations, treatments, and other medical events. This is an owner-entered household reference, not a clinical record system or medical advice service.
- Keep entry creation lightweight: require an associated pet, an event date, and an event type; make title/description, veterinarian, location, notes, treatment details, follow-up date, and relevant document attachments optional. Allow unknown or incomplete details without inventing them. Validate supplied dates, fields, and attachments, and allow authorized edits and corrections.
- Permit eligible supporting documents such as invoices and vaccination certificates, subject to the Home's existing file-storage allowance, supported file restrictions, permissions, privacy, and seven-day individual deletion/recovery rules. Show upload failure clearly; do not claim an attachment was saved when it was not.
- Present history in a readable chronological timeline with recognizable event types, accessible detail views and clear distinction between recorded events and future appointments. Link to the pet profile without mixing medical history with the separate pet-task dashboard widget.
- Do not infer vaccination protection, treatment success, medication adherence, or medical conditions from missing entries. Do not automatically create reminders, recurring medication plans, vaccination-expiry tracking, or advanced health analytics under this decision; those require separate approval.
- Respect Home access controls for viewing, adding, editing, deleting, restoring, and downloading attachments; do not expose private medical details in notifications or shared displays without the applicable visibility rules.
- Acceptance criteria: create each supported event type with minimal fields; add and view optional veterinarian/notes/attachments; handle absent details; reject invalid dates and unsupported/over-quota files; display events in chronological order; edit and recover an event safely; deny unauthorized access; distinguish historical events from upcoming appointments; recover gracefully from partial upload failure.

### Confirmed dedicated pet care schedules (13 October 2026)
- **Approved option B:** Each Home can maintain dedicated one-time and recurring pet-care activities associated with a specific Home-owned pet, including feeding, medication administration, grooming, and veterinary appointments. These are household coordination records, not medical prescriptions or automatic treatment recommendations.
- Allow authorized members to create, edit, pause, resume, and end schedules. Provide a clear activity title, associated pet, schedule/date, and optional time, care instructions, category, responsible member(s), and reminder settings; do not require irrelevant fields. Support the established recurrence patterns and explicit edit scope for one occurrence versus a series, where applicable.
- Assign responsibility only to eligible Home members, subject to Home permissions. Show unassigned care clearly; do not assume the pet owner or schedule creator is responsible. Changes to assignments must respect existing notification preferences and must not imply acceptance or completion.
- Track scheduled occurrences and explicit completion with actor and timestamp, with permitted corrections. Distinguish upcoming, due, overdue, completed, skipped/cancelled, and paused occurrences as applicable. Never infer medication was administered merely because a reminder was sent or a schedule exists. Missed care does not trigger automatic medical escalation.
- Surface upcoming and relevant overdue care in the **separate configurable Home pet-task/reminder dashboard widget**, with pet identity, activity, timing, status, and responsible member when visible. Provide accessible links to the activity and pet profile; do not bury these items inside the profile or duplicate them as unrelated ordinary tasks. Apply wall-display privacy rules.
- Reminders are optional and follow existing member-level delivery preferences, quiet hours, visibility, and anti-spam rules. Medical history entries do not automatically create care schedules, and completing a care activity does not automatically assert a medical-history event.
- Validate pet ownership, Home membership, recurrence, permissions, and record state on each mutation. Handle changes in time zone, daylight-saving transitions, deleted pets, departed members, concurrent completion, partial notification failures, and seven-day recoverable deletion without silently duplicating scheduled occurrences.
- Acceptance criteria: create one-time grooming and recurring feeding/medication care; assign/reassign an eligible member; complete and correct an occurrence; distinguish overdue from completed; edit one instance versus future series; pause and resume; display tasks in the separate widget; respect notification privacy and quiet hours; prevent cross-Home access; handle deleted pet/member and safe retries.

### Confirmed pet medical-information access permissions (13 October 2026)
- **Approved option B:** Keep basic pet profiles and ordinary pet-care schedules under existing Home pet-module permissions, but require **separate, explicit Home permissions** to view and manage sensitive pet medical information. Do not assume pet-module access grants medical access.
- Protect medical-history entries and attachments, medication and allergy details, identification numbers/details, and other clearly sensitive veterinary or health fields. Apply the same restrictions to search, previews, exports, downloads, linked records, notifications, activity logs, and dashboard/wall displays; avoid leaking protected information through titles, counts, thumbnails, or error messages.
- Distinguish permission to **view** sensitive pet medical information from permission to **create/edit/delete** it. Only authorized Home administrators or members with existing permission-management authority can grant/revoke the additional access; permission changes must be auditable and effective immediately, including on open views and downloads.
- Authorized caregivers without medical-history access may still see permitted non-sensitive pet identity and care activities. If a care activity includes medication names, dosages, conditions or sensitive instructions, conceal those protected details from unauthorized members; do not expose them indirectly in the separate pet-task widget. Do not prevent necessary non-sensitive task visibility solely because a linked medical record is restricted.
- Require explicit authorization for opening medical attachments and for restoring deleted sensitive records. Recheck access at the time of each read or mutation, including after role changes, member removal and Home switches. Default newly created sensitive information to restricted visibility; never broaden access automatically.
- Keep this as **category-level Home permissions**, not per-document or per-field member-by-member sharing. The detailed permission matrix and safe handling of mixed public/private fields must be documented in the supporting Pets and Permissions specifications before implementation.
- Acceptance criteria: pet-module-only member can see permitted basic details but not medical entries or attachments; authorized medical viewer can read but not edit; medical editor can update only within permitted Home; medication instructions do not leak through care widgets, wall displays or notifications; revoking permission blocks subsequent reads/downloads; cross-Home access is denied; deleted/restored sensitive records retain protection.

### 4.7 Photos (formerly Memories)
- **Approved option A (13 October 2026):** Replace the ambiguous standalone **Memories** module with a lightweight **Photos** gallery for personal and Home-shared photos. This is a photo-organizing and dashboard-display feature, **not** a digital scrapbook, event journal, or replacement for a full cloud-photo service. Existing references to the former Memories module in the product specification refer to this Photos module unless specifically describing Ora’s distinct long-term assistant memories.
- Members can upload and browse photos, organize them into personal or Home-owned albums, and use configurable photo widgets on their personal or Home dashboards. A photo need not have a separate dated/title/description 'memory entry' to exist. Do not introduce stories, scrapbooks, advanced photo editing, or automatically generated memory events.
- Ownership and visibility must be explicit: personal photos/albums remain private unless deliberately shared through supported controls; Home-owned photos/albums follow that Home's photo-module permissions. Do not silently share across Homes or expose personal photos through Home dashboards or wall displays.
- Album creation, renaming, membership, removal, photo deletion, access changes, upload failures, and seven-day recovery must follow the global privacy, file-handling, storage, and permission rules. Removing a photo from an album must not implicitly delete the underlying photo. Clarify the exact album and photo-sharing interactions in the supporting specification.
- Photo widgets show only accessible selected photos/albums, with empty, loading, restricted, and failed states. Wall displays require their separate display-visibility authorization; never assume Home membership alone authorizes public display.
- Acceptance criteria: upload and browse personal photos; create and populate an album; use an authorized Home-shared album; add an album/photo widget; remove a photo from an album without deleting it; delete and restore within the global recovery window; prevent personal/cross-Home photo leakage; handle upload failures and revoked permissions.


### Confirmed cross-Home photo album sharing (13 October 2026)
- **Approved option B:** A member with the required authority can explicitly share an existing personal or Home-owned photo album with **one or more selected Homes**, without copying the photos or creating independent album versions. The same album and its contents remain synchronized for all authorized audiences.
- Preserve a single authoritative album owner (personal account or original Home). Sharing grants scoped access; it does **not** transfer ownership, make the album public, or allow recipient Homes to reshare it automatically. Require deliberate selection of each destination Home and a clear preview of the audiences and permissions before confirmation.
- Support distinct **view** and **contribute** access for each selected Home, subject to the owning space's rules and each destination Home's permissions. Viewing allows browsing permitted photos; contribution permits authorized members to add photos to that album, but does not implicitly grant album deletion, permission management, ownership transfer, or deletion of photos uploaded by others. Only authorized owners/managers can change sharing or remove an album.
- Clearly distinguish ownership of an album from ownership of each uploaded photo; enforce access to underlying photo assets and thumbnails through the album share without accidentally making the photo available elsewhere. Define how a contributor's photo is retained, removed or deleted, including when the album share is revoked or a member leaves a Home, in the supporting Photos specification. Do not silently delete the original photo when removing it from an album.
- Changes to the album (name, ordering, membership and contents where permitted) are reflected to authorized viewers in all shared Homes. Recheck permission on each read/write and revoke access promptly when a share is removed, Home membership changes, or the owner deletes the album. Previously downloaded files cannot be remotely revoked; explain that limitation when sharing.
- Shared albums are **not automatically shown** in a Home's dashboard photo widget or wall display. Each surface needs explicit selection and its existing display/privacy permissions. Never leak photo counts, thumbnails, titles or files to unshared Homes.
- Handle mixed ownership, duplicate sharing targets, inaccessible destination Homes, removed contributors, simultaneous edits, interrupted uploads, expired access and seven-day recovery consistently with global rules. No sharing with arbitrary external users or public links is introduced by this decision.
- Acceptance criteria: share a personal album with two selected Homes; grant one Home view-only and another contribution; authorized updates appear across Homes; view-only member cannot upload; contributor cannot change sharing or delete others' source photos; unshare one Home without affecting another; remove a photo from an album without deleting its source; revoke access on Home exit; prevent unapproved wall-display exposure; recover an eligible deleted album without unintentionally restoring revoked shares.

### Confirmed photo widget selection and slideshow controls (13 October 2026)
- **Approved option B:** Configurable Photos widgets support displaying **one selected photo**, an **explicitly selected set of photos**, or **one selected album**. Available on personal/Home dashboards and, subject to separate authorization, wall displays. Do not add smart photo selection, collages, themes or advanced animated presentations.
- For each widget, let an authorized editor select its photo source, choose **static display** or **automatic slideshow** where multiple photos are available, set a supported slideshow interval, and select an image-fit behavior (for example, contain or cover). Show an understandable crop preview for cover mode; never modify the original image. Preserve accessible defaults and responsive rendering.
- A selected album may reflect later permitted changes to its contents, but widget source selection and wall-display publication remain explicit. For individually selected photos, preserve the intended selection and do not automatically include newly uploaded photos. Do not silently fall back to unrelated photos when a selection is unavailable.
- Respect each viewer's current access to the underlying photos, album and sharing scope. Recheck permissions as slideshow images change; immediately stop displaying revoked, deleted, restricted or newly inaccessible images. A wall display must only show sources separately authorized for that display, regardless of Home album membership. Prevent private thumbnails, filenames and counts from leaking in loading/error states.
- Pause slideshow advancement when the widget is not visible where feasible and honor reduced-motion preferences. Provide accessible pause/resume and manual next/previous controls for multi-photo presentations, with keyboard and touch operation. Do not force animations on users who request reduced motion.
- Handle empty albums, one-photo albums, removed selections, interrupted uploads, network failure, simultaneous edits and restored photos with explicit safe states. Apply existing widget configuration permissions and persistence rules; avoid unnecessary repeated downloads of full-resolution files.
- Acceptance criteria: single-photo widget; hand-picked multi-photo widget; album slideshow; interval and fit changes; crop preview; one-image fallback; pause/next/previous; reduced-motion behavior; mobile and wall layouts; newly added album photo; revoked shared album; deleted photo; inaccessible selection; empty/error state; unauthorized wall-display source.

### Confirmed Photos storage allowances and capacity feedback (13 October 2026)
- **Approved option B:** Photos uses the existing **separate, platform-administrator-configurable personal and Home file/media storage allowances**. Photo uploads to a personal library consume the owner's personal allowance; uploads to a Home library consume that Home's allowance. Do not introduce a second, independently stacked photo quota unless separately approved.
- Show authorized members the applicable storage pool and its **used, available and total capacity** in Photos upload flows and link to the existing personal/Home storage settings. Show usage after processing based on the retained optimized master and required derivatives, not merely the source upload size. Avoid double-counting one photo used in multiple albums or a shared album across Homes: album access does not copy photo files or transfer quota responsibility.
- Apply the already approved **80% and 95% in-app capacity warnings**, including their role-based recipients, anti-spam behavior and accessible presentation. At 100%, block only operations that need additional file/media capacity; preserve browsing, permitted album organization, metadata edits, downloads and other non-storage actions. Explain the affected pool and possible next steps without promising unapproved upgrades.
- Platform administrators may configure or revise allowance policy for personal spaces and Homes; changing an allowance must not silently delete or degrade existing photos. Validate space before accepting an upload and recheck before committing optimized files, accounting for concurrent uploads, processing outputs and recoverable deleted media. Show truthful failure and retry states; clean up failed temporary files.
- Respect the existing **seven-day deleted-file recovery** and accounting rule: recoverable deleted photos continue consuming their owning pool until permanent deletion. Shared albums and multiple album references do not create separate charged copies; independently copied or transferred media follow the global ownership-transfer accounting rules.
- Exact allowance amounts, price tiers and paid upgrades remain **undecided pending pricing**, and are not authorized by this decision.
- Acceptance criteria: personal versus Home upload capacity; same photo in multiple albums; album shared to two Homes; optimized file plus derivatives counted correctly; 80%/95% warnings only to authorized recipients; exhausted quota blocks uploads but not browsing or album edits; soft-deleted photos still counted; concurrent uploads near limit; administrator lowers allowance below existing usage; retry after processing failure; no cross-Home storage usage leakage.

### Confirmed optimized photo upload and display derivatives (13 October 2026)
- **Approved option B:** On upload, process supported photos into optimized stored images and appropriate smaller display variants for gallery thumbnails, full-screen viewing and dashboard/wall-display widgets. **The optimized image is the retained source; do not retain the uploaded original by default.** This is a deliberate quality/storage tradeoff, not an original-file backup service.
- Clearly disclose before upload that original file bytes, original resolution and potentially some metadata will not be preserved; downloads provide the retained optimized version, not the originally uploaded file. Do not misleadingly label an optimized download “original.” Provide an accessible, understandable indication of upload processing, quality limitations and failures.
- Preserve useful orientation and visual appearance; avoid unnecessary repeated lossy re-encoding, extreme compression, visibly damaging crops, or unexpected distortion. Display-size variants may be cropped only for presentation according to widget fit settings; retain a suitable uncropped optimized master. Specify supported formats, animation/HEIC handling, size/dimension limits, quality thresholds, metadata/privacy policy and processing fallback in the supporting Photos specification, rather than assuming every input can be safely optimized.
- Treat optimization as part of a single validated upload workflow: check type and safety, authorization, available storage allowance, processing outcome and destination ownership before exposing the photo or marking it successful. Recheck quota against **retained optimized files and required derivatives**; explain that the final accounted size can differ from the source upload size. Avoid orphaned originals, incomplete visible assets and duplicate writes on retry.
- Apply the existing personal/Home quota, cross-Home album-sharing, contribution ownership, privacy, deletion, seven-day recovery and permission rules to optimized masters and derivatives alike. Shared album views reuse authorized assets rather than creating independent copies per Home. Revoke access to all variants when photo access is removed, including cached/widget presentation where technically controllable.
- Handle corrupt/unsupported images, insufficient storage, processing interruption, orientation errors, slow uploads, simultaneous uploads, and derivative-generation failures with clear status and safe retry/cancel behavior. Do not silently substitute a lower-quality or different image without disclosure.
- Acceptance criteria: upload supported photo and view optimized gallery/widget versions; download retained optimized version; disclose lack of original retention; handle rotated images; compare contain/cover presentation without modifying master; account for retained assets under correct quota; cross-Home share without duplicating assets; reject unsupported/corrupt files; recover from interrupted processing; block over-quota uploads; revoke thumbnail and slideshow access; restore recoverable optimized photo and its authorized derivatives.

### Confirmed independent photo libraries and optional multi-album membership (13 October 2026)
- **Approved option B:** Photos are stored in an explicit **personal or Home-owned photo library** and can exist without belonging to any album. Albums are optional organizational collections, not required upload destinations. Members with appropriate access can browse the library, including unorganized photos.
- An eligible photo may belong to **multiple albums without duplicating the stored optimized master or display derivatives**. Adding/removing album membership changes only the relationship, not the photo's underlying ownership or existence. Removing a photo from its last album returns it to the library; it does not delete the photo. Deleting the underlying photo is a distinct, explicitly confirmed operation subject to existing seven-day recovery rules and effects on all album memberships/widgets.
- Keep the photo's **single authoritative owning library** (personal account or one Home), independent of how many albums reference it. A cross-Home-shared album grants only its approved view/contribute access to included photos, not general access to the owning library, other albums, or unorganized photos. Recheck photo and album permissions for each view, download, edit, membership change, widget and wall-display presentation.
- Contributors to shared albums retain the applicable original photo ownership; adding an authorized photo to a shared album must not silently move it to the recipient Home or create a second master. A member must not add photos they cannot access or share. Explicitly explain the broader album audience before a photo is added to a shared album. Revoke derived access when membership/sharing is removed without deleting the source photo.
- Allow permitted bulk selection for assigning or removing photos from albums, with a review of the destination album and any sharing consequences. Do not automatically classify, group, tag or create albums based on photo content, dates or location. Show clear empty-library, empty-album, unorganized and inaccessible-photo states.
- Define the detailed cross-owner album membership, contributor departure, account/Home removal and quota responsibility rules in the supporting Photos specification; preserve the already approved ownership, quota, permissions and shared-album semantics without silently transferring files or ownership.
- Acceptance criteria: upload a photo with no album; find it in its owning library; add it to two albums without duplicate storage; remove it from one and then all albums while retaining the photo; delete/restore the underlying photo with affected album references handled safely; add an authorized personal photo to a Home-shared album without exposing the rest of the personal library; revoke an album share without deleting contributor photos; enforce quotas, permissions, widgets and wall-display restrictions.

### Confirmed context-aware photo removal and library deletion (13 October 2026)
- **Approved option B:** From an album, provide two clearly distinct actions when authorized: **Remove from this album** (remove only the album membership) and **Delete from library** (delete the underlying photo from its authoritative personal/Home library). Use unambiguous labels, separate permissions, and do not make a destructive library deletion the default album action.
- Removing an album membership preserves the optimized master, derivatives, other album memberships, and library availability. Explain if removing it from a shared album also ends access for members or Homes whose access depended on that album; do not remove other independent access routes.
- Before deleting a library photo, present an explicit, accessible impact preview identifying the owning library, affected album memberships, any shared Homes or audiences that will lose access, and photo widgets or wall displays that may be affected, without revealing unauthorized private album names or membership details. Require explicit confirmation; cancel must make no changes. If a member can remove from an album but cannot delete from the library, do not offer a usable library-delete action.
- Library deletion follows the global **seven-day recoverable deletion** policy and storage accounting. The photo and all derived sizes become unavailable across every album, shared Home, search, widget and wall display immediately; restoration by an authorized member should recover the photo and eligible album references where those relationships and permissions still exist. Do not automatically recreate revoked shares or deleted albums.
- Recheck photo ownership, album membership, deletion authority, Home context, sharing state and dependent references at confirmation/execution. Handle concurrent removals, revoked permissions, already-deleted photos, partial failures and retries without deleting the wrong asset or duplicating changes. Record relevant deletion and restoration actions in the existing audit/history mechanisms.
- In library views, offer the authorized library-delete action with the same impact preview; distinguish it from removing an item from a selected album. Multi-select must not silently turn album removal into bulk library deletion. Keep the interface mobile-friendly and keyboard/screen-reader accessible.
- Acceptance criteria: remove one photo from one of three albums while retaining the library photo and other memberships; remove from the last album without deleting the photo; remove from a shared album and revoke only album-derived access; deny library deletion to a contributor lacking authority; confirm library deletion with multiple albums and shared Homes; cancel without changes; ensure widgets stop displaying deleted photos; restore within seven days without recreating revoked shares; handle a concurrent permission change and safe repeated request.

### 4.8 Integrations
- **Google Calendar is a committed MVP integration**, including inbound event synchronization and outbound event creation. Spotify has been discussed, but its exact MVP behavior must be checked against the original scope.
- Integrations are **conditional on actual provider capabilities and authorization**; never assume access or promise unsupported actions.
- Native Madeora data and features remain functional without them.
- Show disconnected, authorization-expired, loading, stale, and failed states honestly.
- Never display stale or failed synchronization as successful.
- Preserve Madeora-owned data when external integrations fail or are disconnected.
- Provide practical supported alternatives when an integration is unavailable.

### 4.9 Dedicated wall display
- A purpose-built display mode for a household screen, distinct from the desktop app layout.
- Prioritize glanceable shared information and legibility at distance.
- Define access and privacy safeguards before exposing private personal data on a shared screen.
- Exact hardware, kiosk behavior, and interaction methods remain to be specified.
