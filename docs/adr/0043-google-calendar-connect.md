# ADR 0043: Google Calendar connect and inbound sync

- **Status:** Accepted for S33 within the approved architecture (§7, §9, §15, §21, §31, §34, §36, §39), CLAUDE.md (authentication A, authorization C, database access A, background processing B, configuration A, observability B, €0 budget), ADR 0010 (Google sign-in), ADR 0017 (background jobs) and ADR 0042 (native calendar). The defaults in the brief (`plans/steps/S33-brief.md`, "Defaults picked") are open to correction by the owner.
- **Date:** 2026-11-05
- **Step:** S33 (brief: `plans/steps/S33-brief.md`).

## Context

The spec (Modules.md §4.2 and §4.8, PS journey 7 and §11.2) lets an adult connect Google Calendar, choose which calendars appear on their personal calendar and which Homes see them, and requires that unshared calendars reveal nothing, that sync states are never shown as better than they are, and that losing Google's authorization leaves native features working with a truthful warning. The done-condition for this step is that tests cover revoked consent, invalid sync token resync and duplicate prevention. Writing to Google is S34.

## Decision

**A separate Google Cloud project.** Calendar access uses its own project ("Madeora Calendar") and OAuth web client, never the sign-in project's (ADR 0010), so the sensitive calendar scopes never touch sign-in's consent screen and signing in with Google never connects a calendar. It runs in Testing status until Google's verification before public launch; in Testing, Google ends refresh tokens after 7 days and the person reconnects. Configuration is three server-only variables (`GOOGLE_CALENDAR_CLIENT_ID`, `GOOGLE_CALENDAR_CLIENT_SECRET`, `GOOGLE_CALENDAR_TOKEN_KEY`), all or none, validated by `@madeora/google-calendar`; unset, Settings says Google Calendar is not available and nothing contacts Google.

**OAuth.** A same-origin form POST (CSRF, §7) by a signed-in person creates a random state and a PKCE S256 verifier, kept for 10 minutes in a cookie sealed with AES-256-GCM (httpOnly, SameSite=Lax, path limited to the callback, bound to the person), and sends the browser to Google with `calendar.calendarlist.readonly` and `calendar.events` (the narrowest pair that reads the list and reads, and in S34 writes, events), offline access and forced consent. The callback uses the cookie once and accepts only the same person and state within the 10 minutes; it exchanges the code with the verifier, requires both scopes and a refresh token (otherwise it revokes the grant and stores nothing), and reads the primary calendar id as the account label.

**Tokens at rest.** The refresh token is sealed with AES-256-GCM (`v1.<iv>.<ciphertext>.<tag>`, base64url) under `GOOGLE_CALENDAR_TOKEN_KEY`, with `madeora:google-calendar:refresh-token:<user id>` as associated data, so a token copied to another person's row does not open. The database checks the format and never returns the token to a person; only disconnect hands it back once (to revoke it) and the sync job reads it with the service role. Access tokens live in memory for one run. Logs carry event names and short codes only.

**Model.** `private.google_calendar_connections` (one per person), `private.google_calendars`, `private.google_calendar_home_shares` (keyed to the owner's membership, cascade on leave) and `private.google_calendar_events` (one row per expanded instance, unique per calendar and Google id). No table is granted to an API role; people use security-definer functions with their own session, and the job uses service-role-only functions that recheck the connection and its lease.

**Sync.** The outbox job `google-calendar-sync` (one per connection, version 1, 4 attempts) takes a database lease (one run per connection), refreshes the access token, refreshes the calendar list (the first list turns on the primary calendar, shown personally; a calendar Google no longer lists becomes unavailable and loses its events and shares), then syncs each chosen calendar: incremental with its sync token; a full pass over 30 days back to 365 days ahead (`singleEvents=true`) when there is no token, when Google answers 410 (invalid sync token: the token is cleared and the pass restarts) or when the last full pass is over 24 hours old. Pages are applied idempotently: within a page the last item per id wins, rows are upserted on calendar and Google id, and cancelled instances or series are deleted; a full pass marks what it saw and finishing deletes the rest. More than 5000 events fails the calendar with `too_many_events`. It is queued on connect, when a calendar is turned on and by Sync now (together at most once a minute per person, so calling the functions in a loop cannot flood the job queue), and every 15 minutes for each connected account that has a calendar to sync (or has not been listed yet) by the existing 5-minute dispatcher's `prepare` hook (no extra schedule). The job's writes lock the calendar row, so turning sync off during a run never leaves events or a sync token behind. Push channels are left for later.

**States and privacy.** A calendar is `syncing`, `synced`, `stale` (no success for over an hour), `failed` (with a code), or the connection is `authorization_expired` (Google refused the refresh: revoked consent or an expired Testing token). The owner sees the exact state and reason; Home members see only "not up to date" and the last sync time of a shared calendar. On expiry syncing stops, the last-synced events stay visible with the warning, the person gets one in-app `security` notice (`google_calendar.authorization_expired`, no email) and a Reconnect button. Google events join the native calendar reads (`list_calendar`, `get_calendar_upcoming`, a read-only event page) with `source: "google"`; a Home sees a calendar's events only when its owner shared it there, never events Google marks private or confidential, and an unshared calendar reveals no event, time, count, name or state anywhere. Turning a calendar's sync off deletes its events and shares; disconnect revokes at Google (best effort, the page says when it could not) and deletes everything.

**Interface and API.** Settings › Google Calendar (`/settings/google-calendar`): connect, account and state, Sync now, Reconnect, Disconnect with a confirmation, and each calendar's choices. Routes: `POST /api/v1/integrations/google-calendar/connect`, `GET …/callback`, `GET` and `DELETE /api/v1/integrations/google-calendar`, `POST …/sync`, `PUT …/calendars/:id`, `GET /api/v1/calendar/google-events/:id`.

## Consequences

- Google's API is free within its quotas and needs no billing account; the 15-minute polling with sync tokens stays far below them (`docs/provider-cost-register.md`).
- Each connected account costs about 2,880 Trigger.dev runs a month, an estimated $0.30 to $0.50 of the $5 free budget; roughly 7 to 10 accounts fit. The interval is one limit (`auto_minutes`) if it must grow.
- Known limits: a request that arrives while a run holds the lease waits for the next automatic run (up to 15 minutes); the widget's warning shows the state without the time (the calendar page shows both); one key protects both the stored tokens and the connect cookie, separated by their associated data.
- In Testing, everyone who connects must be a listed test user and reconnects weekly. Verification of the sensitive scopes must be planned before public launch.
- Changing `GOOGLE_CALENDAR_TOKEN_KEY` makes stored tokens unreadable: affected connections become `authorization_expired` and people reconnect. There is no key rotation in this step.
- CI never contacts Google: unit tests use a fake Google, route tests a fake client, Playwright checks the not-configured state, and the database tests run the sync functions directly.
