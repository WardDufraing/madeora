# ADR 0044: Google Calendar outbound changes and conflicts

- **Status:** Accepted for S34 within the approved architecture (§9, §15, §21, §31, §34, §36), CLAUDE.md (authorization C, database access A, background processing B, date/time A, observability B, €0 budget), ADR 0017 (background jobs), ADR 0042 (native calendar) and ADR 0043 (Google Calendar connect and inbound sync). The defaults in the brief (`plans/steps/S34-brief.md`, "Defaults picked") are open to correction by the owner.
- **Date:** 2026-11-05
- **Step:** S34 (brief: `plans/steps/S34-brief.md`).

## Context

Modules.md §4.2 lets a person create events in a configured Google calendar from Madeora, edit Google events and have the edits sync, asks them to resolve conflicts instead of resolving them silently, gives deletion two choices ("Remove from Madeora" with an exclusion, or delete in Google), supports the three recurrence scopes, and requires provider limits to be reported honestly. The done-condition is that the "Google Calendar" journey passes and no conflict resolves itself. S33 stored Google events read-only (ADR 0043).

## Decision

**A Google event stays a Google event.** An event saved to Google is a row of `private.google_calendar_events` that Madeora shows and edits, never a native event with a copy. Participants, reminders and per-event Home sharing stay native-only (a Google event reaches a Home through its calendar's share). Only personal events go to Google; Home events stay in Madeora.

**Changes wait in the database.** Every change from Madeora is one row of `private.google_calendar_changes` (no API grant): action `create`, `update` or `delete`; scope `event` (one event or one occurrence), `following` or `all`; `base` (the Google version the person changed, with its etag), `mine` (Madeora's version) and, in a conflict, `theirs`. One open change per event (or per series), so a second edit merges into the waiting one. Each change moves a `version`, so a result for an older version never drops a newer edit. A single event's new values show in Madeora at once (the stored row takes them, and its `revision` moves); a series change shows once Google has it, with the next pull; the page sends the revision it showed, so an edit from an older page answers `stale`.

**Pushing.** The existing `google-calendar-sync` run, inside its lease, sends open changes first (at most 50 per run), then pulls as in S33. Updates and deletes carry `If-Match` with the base etag. New events get an id Madeora chose (`madeora` + an md5 of the person and the request id; a split series `madeora` + the change id), so a retried job or a repeated request never makes a second event and Google's 409 counts as done. Answers: 2xx done (the row takes Google's version); 412 reads the event and reconciles; 404/410 on an update is "deleted in Google" (a conflict), on a delete done; 401 ends the run as `authorization_expired` and every change waits; 5xx, 429 and network errors leave the change pending with a code (20 attempts, then failed); 400/403 fail it. A change made during a run queues a follow-up run when that run ends.

**Field-level reconcile, never automatic resolution.** The fields are title, location, description and time. When Google's version differs from `base`, fields changed on one side only merge (Madeora's change is narrowed to what Google has not changed); a field changed on both sides to different values makes the change a `conflict` holding both versions. Google deleting an event Madeora edited, and Google editing an event Madeora is deleting, are conflicts too. A full pass takes only an event inside its window (30 days back, 365 ahead) for deleted when it does not list it, and never replaces a conflict's Google version that way. An answer Madeora cannot read is never taken for a deletion. Nothing but the owner's choice ends a conflict: no apply, page, full pass, finish, retry, timer or job changes its state. "Keep Google's version" applies `theirs`; "Keep Madeora's version" requeues `mine` with `theirs` as the new base and etag, so another Google change in between makes a new conflict, not an overwrite. While a conflict waits the event is shown with the stricter of the two privacy flags, so a Home never sees a version made private.

**Recurrence and time.** Timed events go to Google as a local wall-clock time plus the IANA zone, so a series keeps its time across DST; a time in a DST gap is refused as for native events. Madeora's repeat rule becomes one RRULE: daily, weekly on weekdays, monthly on days 29 to 31 with `BYMONTHDAY=28,…,d;BYSETPOS=-1` (the last-day fallback), yearly on 29 February with `BYMONTH=2;BYMONTHDAY=28,29;BYSETPOS=-1`, every n, until a local date (in UTC for a timed series, as RFC 5545 requires) or n times. "This and following" inserts the new series first and then ends the old one with `UNTIL` one second before the occurrence (the day before for all-day). Series scopes change the text, the time of day and the length, never an occurrence's date or the kind of event, and Madeora never edits a Google series' repeat rule. A counted series (`COUNT`) and a series with extra dates (`RDATE`) are refused for a split with `series_limit` and the page says to change it in Google Calendar. A split at the series' first occurrence replaces the old series; if Google refuses to end the old series, the new one is deleted again, so Google never keeps both. The new series copies the old one's text, visibility, availability and colour, not its guests or Google reminders. A new repeating event cannot be edited until Google has it, and choosing Madeora's version of a series Google deleted fails with `series_limit` (Madeora does not recreate series).

**Deletion with two choices.** "Remove from Madeora" writes a row of `private.google_calendar_exclusions` (one event, a whole series, or a series from one occurrence on), works on any synced calendar including read-only ones, never calls Google, hides the event from every Madeora read (personal and Home calendars, upcoming, the event page), survives every resync, and is listed in Settings with Restore. "Delete everywhere" names the Google calendar, needs a writable calendar, and keeps the event visible as "Being deleted from Google" until Google confirms; a failure shows Try again and Discard, never a silent local-only removal.

**Owner only.** Only the calendar's owner sees the change, edits, deletes, resolves, retries, discards and restores; anyone else, and every forged id, gets `not_found`. Editing and "Delete everywhere" need a calendar Google lets them write (owner or writer). A calendar cannot stop syncing while it has open changes. Disconnect drops the changes that have not reached Google, and its confirmation says so.

**Interface and API.** The Google event page shows the waiting change, the conflict comparison with its two choices (named "Restore in Google"/"Accept the deletion" and "Delete anyway"/"Keep the event" when one side deleted it), and Edit and Delete for the owner; `/calendar/google/:id/edit` edits it, with the three scopes and a dry run listing the affected occurrences. The personal new-event form offers "Save to" Madeora or a writable Google calendar (default: the target). Settings adds "New events go to", the list of changes waiting for Google, and the removed events with Restore. Calendar lists mark the owner's events as saving, deleting, conflict or not saved. Routes: `POST /api/v1/calendar/google-events`, `PATCH` and `DELETE /api/v1/calendar/google-events/:id`, `PUT /api/v1/integrations/google-calendar/target`, `POST …/changes/:id`, `DELETE …/hidden/:id` (`apps/web/src/google-calendar/api.ts`).

## Consequences

- No new service, schedule or cost: changes ride the existing job run, which already holds the lease and an access token. Google's quotas are far above one person's edits.
- When Google stops listing a calendar, its events leave Madeora (as in S33) and so do its waiting changes and conflicts, since nothing can be sent there any more. The owner may prefer otherwise; this is listed for their decision.
- Conflicts may wait indefinitely; that is intended (the spec forbids silent resolution). Settings lists them.
- Occurrences removed from Google by a split may stay in Madeora until the next full pass (at most 24 hours), as for any change S33 learns about late.
- Monthly days 29 to 31 and 29 February rely on Google honouring `BYSETPOS`, which RFC 5545 defines and Google documents; if a calendar shows otherwise, the event can still be changed in Google.
- A description longer than Madeora's limit cannot be saved from Madeora until shortened; Google's own copy is unchanged.
