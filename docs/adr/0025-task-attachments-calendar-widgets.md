# ADR 0025: Task attachments, calendar view and task widgets

- **Status:** Accepted for S19c within the approved architecture (§10, §15, §36, §37), CLAUDE.md (database access A, authorization C, file storage B, data fetching B, forms A, frontend B, date/time A, dashboard layout B, €0 budget) and the spec's task document and image attachments, deletion and recovery of parent items with attachments, optional task calendar views and configurable task dashboard widgets. The owner confirmed the attachment formats and limits on 20 Oct; the other defaults below are open to correction by the owner.
- **Date:** 2026-10-20
- **Step:** S19c (brief: `plans/steps/S19c-brief.md`). Builds on S15 (file storage, ADR 0019), S16 (trash, ADR 0020), S17 (dashboard, ADR 0021), S18 (tasks, ADR 0022) and S19 (recurring tasks, ADR 0023).

## Context

People attach documents and photos to tasks, see their tasks on a week or month calendar, and put configurable task lists on their dashboards. Attachments are the first files other people see, so every view must follow the task's visibility at that moment, and a file that was not checked must never appear as saved. The spec does not set the allowed formats or limits, and architecture.md says not to invent them: the owner chose them on 20 Oct (images plus common documents, 10 MB per file, 10 per task).

## Decision

**One migration** (`20261029090000_task_attachments_calendar_widgets.sql`) adds `private.task_attachments` (a file linked to a task), `private.task_series_attachments` (attachments on a series chain), `private.task_attachment_uploads` (the task a pending upload is for), the attachment, calendar and impact functions, three timing filters on `list_tasks`, and the trash item types `task_attachment` and `task_series_attachment`. The tables have no grants; everything goes through `security definer` functions with the person's session.

**Formats and limits (confirmed by the owner, 20 Oct).** JPEG, PNG, WebP, PDF, TXT, CSV, Word, Excel, PowerPoint (OOXML) and OpenDocument text, spreadsheet and presentation; at most 10 MB per file and 10 attachments per task (`private.task_limit('attachments')`), counting uploads in progress. Legacy Office formats, SVG, HTML and archives are refused. The browser falls back to the file extension when it reports no type, and the server checks the bytes either way.

**Upload: the S15 pipeline with a new purpose.** `create_task_attachment_intent` checks that the task is visible and editable, the type, size and count, the rate limit and the **task's pool** (the person's for a Personal task, the Home's for a Home task) under the S15 locks, and stores the sanitized display name. Finalize reads the bytes back and dispatches by the upload's purpose (`tasks/attachment-file.ts`): images are decoded within the S15 pixel limits and **re-encoded in their own format without any metadata** (location, camera), with the orientation applied; PDF must start with `%PDF-`; text must be UTF-8 without NUL bytes; Office files must be ZIP packages with `[Content_Types].xml` and the right part folder; OpenDocument files must carry their stored `mimetype` entry. Re-encoded pictures must still fit 10 MB. Then `finalize_upload` (unchanged) and `attach_task_file` with the person's session, which re-checks the task and rights at that moment. A ready file nobody attached is retired by the existing expiry job. Retry continues the same attempt: the same request id, and once the bytes are stored only finalize again, so a retry never opens a second upload or attaches a second copy. There is no malware scanner: none fits the €0 budget, so safety is the allowlist plus the real signature check, and downloads of anything but images and PDFs are sent as `attachment`.

**Downloads follow the task.** `authorize_file_read` now also answers for a file linked (not in the trash) to a task the viewer may see now: the Personal space's owner, or a current member of the task's Home. Every other case gets the same 404. The content route redirects to a 60-second link; images and PDFs are shown inline, everything else (and `?download=1`) is an attachment with the display name (`filename*` in UTF-8, an ASCII fallback). The display name is sanitized on both sides: no folders, no control, invisible or direction characters, at most 200 characters with the extension kept.

**Rights.** Whoever may see the task sees and downloads its attachments; its editors (S18) add and remove them; changes for following occurrences or the entire series need the S19 series right. Rechecked on every call.

**Trash and recovery.** Removing an attachment is a trash entry for 7 days and the file keeps counting. Restoring refuses with `task_unavailable` when the task is gone or in the trash and `attachment_limit` when the task already has 10. Deleting a task takes the files no other active task uses into the trash with it; they come back together. Rows are deleted only when an entry is purged, and a trigger then releases a file no row references any more.

**Recurring tasks.** Attachments are either the occurrence's own or from the series (labelled). Adding or removing asks the scope (this, this and following, entire series), with a dry-run impact preview; new occurrences get the series' attachments; completed and individually changed occurrences are never touched. A series-wide file can only be added from an open occurrence, and a chain holds at most 10 series attachments. A file attached to one occurrence on its own makes that occurrence "changed on its own", so a later schedule change keeps it (and the file) instead of deleting it. A series-wide removal is one trash entry that restores the series attachment and its occurrence links together. One file linked from many occurrences is stored and counted once. Removing occurrences with the series (S19) keeps their files linked and counted; they come back with the occurrences, and purging that entry releases the files nothing else uses.

**Calendar view.** `…/tasks/calendar` (personal and Home), reached from a List / Calendar switch; lists stay the default. Week and month views with previous / today / next and the list filters, all in the address. `list_task_calendar` returns a window of at most 42 days and 500 entries (with a `truncated` flag): tasks on their due dates, a "starts" entry on their start dates, and the planned dates of active series that have no occurrence yet, which open the series' current task. Dates are plain dates in the context's timezone and "today" comes from the database, so daylight-saving changes cannot move a task to another day. Tasks without a due date are counted and linked to the list's "No due date" filter. Choosing a day lists its tasks to complete or open. Small screens get an agenda of the days with tasks instead of the grid.

**Task widgets.** A new widget type `tasks` in the S17 registry: on the personal dashboard (Personal tasks), on a Home dashboard, and on the personal dashboard bound to one Home. Settings: one list or All Tasks, status, timing, priorities, labels, assignee (Home only) and 5 / 10 / 15 rows, read again at render so a deleted list, label or departed member shows a safe state and never someone else's data. Rows come from `list_tasks` with the viewer's session; completing uses the per-row right and the subtask confirmation. The personal starter layout gains a Personal tasks widget (spec L427); saved dashboards are untouched.

## Consequences

- Task files count against the same pools as every other file; the owner's allowances (docs/file-storage.md) apply.
- Changing the formats or limits later is a change to `private.task_attachment_type`, `private.task_limit` and `tasks/attachment-policy.ts` together, with their tests.
- Issued download links work for up to 60 seconds after access is lost (ADR 0019).
- No Realtime: attachment, calendar and widget views refresh after the viewer's own changes and on navigation.

## Not done here

The main Calendar's "Show tasks" overlay (Calendar module), wall-display presentation, attachment folders, versions or annotations, copying attachments into templates (excluded by the spec), and a malware scanning service.
