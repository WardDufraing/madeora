# ADR 0047: Adult account security

- **Status:** Accepted for S37 within the approved architecture (§7), CLAUDE.md (authentication A, authorization C, database access A, €0 budget) and ADR 0007/0010 (S06 accounts, S08 Google sign-in and sign-in methods). The defaults in the brief (`plans/steps/S37-brief.md`, "Defaults picked") are open to correction by the owner.
- **Date:** 2026-11-05
- **Step:** S37 (brief: `plans/steps/S37-brief.md`). Trusted devices, backup email, account recovery codes and Google reauthentication are in this step too (Ward, 2026-11-06: one S37 step).

## Context

The spec (Project-specification "Confirmed optional adult two-factor authentication", "Confirmed routine adult password changes and session revocation", "Confirmed adult email address changes", "Confirmed device and session management") asks for optional authenticator-app two-factor sign-in with recovery codes, password and email changes behind recent reauthentication, a list of the account's sessions with sign-out, reporting and "sign out everywhere", and immediate effect of every revocation. Supabase Auth provides TOTP factors, AAL levels, sessions and the change flows; it does not on its own require reauthentication, limit attempts, offer recovery codes or refuse a revoked session's still-valid access token.

## Decision

**Supabase Auth runs the factors; the database decides when.** TOTP enroll, challenge and verify are Supabase Auth's (free; phone factors stay off). Triggers on `auth.mfa_factors`, `auth.mfa_challenges` and `auth.users` enforce Madeora's rules whatever client calls Auth: only TOTP; adding or removing a verified factor, changing the password and starting an email change each need a one-time permission from `authorize_account_change`, which itself needs a password sign-in within 5 minutes and, with two-factor on, an aal2 session with a recent TOTP verification (the S08 pattern, now shared with `authorize_sign_in_method_change`). A permission lasts 2 minutes and is bound to the browser session that asked for it. A password change is checked again at commit: Supabase Auth signs out every session except the one that sent the change, so if any session other than the bound one is left (a stolen session racing the owner), the change is refused. A password reset by email link (amr `otp`) is allowed only if the session left at commit is such a reset session. Supabase's own rehash at sign-in stays allowed. Recovery-code creation checks the bound session directly. At most 10 challenges per factor in 15 minutes; a challenge can succeed only within 30 seconds of its creation (Supabase Auth records no wrong code and lets a challenge be retried until it expires, so this is what makes the challenge limit a limit on guessing time); a second successful code within 90 seconds is refused (replay).

**Recovery codes in the database.** Ten single-use codes, stored only as SHA-256 hashes, shown once. Redeeming one (5 failures per 15 minutes) removes the lost authenticator and the codes, ends every other session and notifies the account; the session then needs no second step.

**An unfinished second step is not signed in.** `getAuthState` on the server reads the verified user and the token's AAL; a session with a verified factor at aal1 sees only `/sign-in/two-factor`, whatever the first step was (password or Google).

**Revocation takes effect on the next request.** PostgREST runs `public.check_request` before every request (`pgrst.db_pre_request`): a token whose session no longer exists, or an aal1 token of an account with two-factor that is not a trusted browser's, gets 401. Exempt are only calls that check the second factor themselves: redeeming a recovery code, using a trusted browser, and the two reauthentication permissions (`authorize_account_change`, `authorize_sign_in_method_change`), which the short-lived password or Google session asks for. It runs with the caller's rights (no SECURITY DEFINER function in `public`) and calls one narrowly granted private helper. The setting is its own migration, so a hosted refusal fails only that step. Realtime does not go through PostgREST, so the two signal tables used by live views get a restrictive policy with the same check. Signing out one session, reporting it and signing out everywhere need no reauthentication, so a suspicious session can be stopped at once.

**Trusted browsers.** After the code, the account holder may tick "Trust this browser for 30 days". The server makes a random token, keeps it only in an httpOnly cookie (one per account, named by a hash of the account id) and stores its SHA-256 hash with the browser and platform; trust is never renewed, at most 10 per account. At the next sign-in the two-factor page hands the token to `use_trusted_device`, which marks that session as past the second factor when the token, browser and platform match (the token stays aal1; `getAuthState`, the pre-request check and the Realtime policies all ask the database). A password, email or two-factor change, a reported session, "sign out everywhere", a recovery and any change to the recovery methods end all trust; signing out one session ends its browser's trust. Supabase Auth ends every aal1 session of the account whenever a code is verified, so where the code for a sensitive change is verified matters: normally on the short-lived reauthentication session (after the password or Google), because the browser's own session is already aal2; on a trusted browser, whose own session is aal1, on that session first (before the password or before leaving for Google), which makes it aal2, and only then does the short-lived session start. Either way neither session ends the other.

**Recovery methods.** A verified backup email (single-use link, 1 hour, opened while signed in as the account; never another account's sign-in or backup address) and ten account recovery codes (16 characters, hashed, shown once) are separate from the two-factor recovery codes. Someone who lost both password and mailbox (Ward, 2026-11-06) enters the sign-in address; a link goes to the backup address (3 a day, same answer whether or not an account exists); with the link and one account recovery code (5 failures per 15 minutes) a 72-hour wait starts and the sign-in address and the app are told, so the owner can stop it under Settings › Security. After the wait a finishing link (7 days) makes the backup address the sign-in address, ends every session and trust, clears the old password and every outstanding reset or one-time link, uses up the codes and removes the backup address; the authenticator is removed only if "I also lost my authenticator" was ticked. A new password follows through the ordinary reset email. These emails go through the job outbox (`security-email`, `account-recovery-ready`) with Resend; their tokens are erased once the send is recorded. The signed-out steps run through invoker wrappers in `public` and allowlisted private helpers.

**Google reauthentication.** An account without a password confirms with Google instead: a separate PKCE client keeps its verifier and short-lived session in sessionStorage (never the session cookies), Google is asked to show the account chooser with this account's address suggested, `/auth/reauthenticate` checks the Google session is this account's, asks for the code when two-factor is on (on a trusted browser before leaving for Google, see above), takes the same one-time permission (an `oauth` sign-in counts as fresh) and signs the Google session out; the change then opens without asking again. Linking Google (S08) now also needs the code.

**Email change.** One confirmation link to the new address (Secure email change off); the old address keeps working until then and is notified afterwards. Asking for an address that is in use looks like success (no enumeration).

## Consequences

- Each hosted project needs the settings in `docs/adult-security-setup.md`. If hosted Supabase refuses the pre-request setting (its own migration), revoked sessions keep working until their access token expires (at most an hour) until the owner picks a fallback.
- Residual risks the owner accepts with this design: Supabase Auth's own writes carry no session, so the email-change and authenticator permissions cannot be tied to a session at the moment of use; within their 2 minutes another live session of the same account could use them. Wrong TOTP codes are limited per IP by Supabase Auth and per account only through the challenge limit and the 30-second window (about 5 minutes of guessing per 15 minutes); the paid Supabase verification hook is not used (€0). A reauthenticated caller can still learn from Supabase Auth's raw answer whether an address is in use, within the 2-minute permission.
- Redeeming a recovery code removes the authenticator at once (no waiting period); the owner chose this on 2026-11-06 (decision in the S37 thread). The delayed recovery for people who have lost both password and mailbox has a 72-hour wait (also 2026-11-06).
- Residual risks of part two: someone who knows an account's sign-in address can use up its 3 recovery links a day (they go only to the backup address); the signed-out recovery steps have no Turnstile check (PostgREST cannot verify one), only the per-account database limits, so calls spread over many accounts that have a backup address can use up part of the free Resend quota; a linked Google identity still signs in after a recovery; the old sign-in address is told when the wait starts (72 hours to stop it), not again at the end; any live session of the account can stop a recovery without reauthentication (stopping only takes something away); the reset form asks for the authenticator code only, so someone who lost both password and authenticator but kept the mailbox uses account recovery (backup address, code, 72-hour wait, "I also lost my authenticator"); choosing an unlinked Google account at "Confirm with Google" creates an empty Madeora account (S08's sign-in rule), which the page then refuses and signs out; a trusted browser's cookie copied to another machine with the same browser and platform also skips the code until trust ends; because Supabase Auth ends every aal1 session of the account when a code is verified anywhere, a trusted browser's current session is signed out whenever the account holder enters a code on another device (its trust stays, so the next password sign-in there still skips the code); on a trusted browser a wrong password after a right code means waiting for the next code (the code was already used).
- Sign-in and session-creation audit events are not recorded yet (S38 audit step).
- No service-role key, extra session system or paid service was added.
