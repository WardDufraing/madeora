# ADR 0045: Photo libraries and processing

- **Status:** Accepted for S35 within the approved architecture (§10, §36, §37), CLAUDE.md (authorization C, database access A, file storage B, background processing B, €0 budget), ADR 0013/0019 (S15 storage and the one privileged call) and the S16 trash. The defaults in the brief (`plans/steps/S35-brief.md`, "Defaults picked") are open to correction by the owner.
- **Date:** 2026-11-05
- **Step:** S35 (brief: `plans/steps/S35-brief.md`).

## Context

Modules.md §4.7 adds a lightweight Photos module: personal and Home libraries, albums with optional multi-album membership, an optimized master with display derivatives where the uploaded original is not kept, storage accounted per pool, and the seven-day recovery of the global rules. The supported formats and limits were open in the spec; the owner decided them for S35.

## Decision

**One library per owner.** A photo belongs to exactly one library: a person's (visible to them only) or a Home's (visible to its current members). Albums belong to the same library as their photos; a photo may be in many albums and taking it out of an album never deletes it. Nothing is exposed as a table; people act through security-definer functions with their own session that recheck the confirmed caller and membership on every call. Cross-Home album sharing, the photo widget and the slideshow are S36.

**Home rights.** Every current member sees the library and uploads. The uploader deletes their own photos and manages the albums they created; the Owner and Administrators granted the new delegable capability `manageHomePhotos` do both for everyone. A personal library is its owner's alone. These rules are one database function (`private.can_change_photo_item`) and the engine (`home.photos.*`) mirrors the capability.

**Processing at finalize, on the S15 pipeline.** The upload intent, the signed PUT and the server-verified finalize are unchanged. For a photo the server checks the signature against the declared type, refuses a header claiming more than 50 megapixels or 12 000 pixels on a side before decoding, decodes (HEIC with the ISC-licensed `heic-decode` over `libheif-js`'s WebAssembly build, because sharp's prebuilt libvips has no HEVC decoder; everything else with sharp), turns the picture upright, keeps the first frame of a GIF, and re-encodes once as WebP into four pictures: a master (long side 2560 px at most) and `full` (1920), `display` (1024) and `thumb` (320), never enlarged and never cropped (cover is a presentation matter). Re-encoding drops all metadata. The upload object is deleted: the original is not kept. Processing is synchronous in the finalize request, like the earlier image purposes, not a Trigger.dev job (one small image, the person waits; ARCH §37 names a job, which S36 or an owner request can add if large HEIC files make requests too slow).

**Four objects, one stored file.** The master is the file's own object; the three derivatives have keys generated by the database when the upload is opened (`private.photo_variants`). `public.finalize_photo` (service role only) validates the four facts, finalizes the file with their total size under the pool lock, and creates the photo, so a photo is never visible half stored and the pool is charged for all four exactly once, also while the photo waits in the trash and however many albums it is in. Triggers on `stored_files` queue every derivative object for deletion when a photo's file fails, is purged or is deleted outright, so the shared purge paths needed no change.

**Reads are authorized per request.** `GET /api/v1/photos/:id/content?variant=` asks `authorize_photo_read` with the viewer's session each time, then redirects to a 60-second signed link; every refusal is the same 404. The generic file route knows nothing about photos.

**Trash.** Deleting photos and albums uses `trash_move` (module `photos`, item types `photo` and `photo_album`). A photo trashed keeps its album memberships, so restoring puts it back where it was; its file keeps its pool charge. Early or expired purge removes the photo, its memberships and (through the file) all four objects. A photo's entry is visible to whoever deleted it and to photo managers.

## Consequences

- New dependency `heic-decode` (ISC) pulling `libheif-js` (LGPL-3.0, unmodified, used server-side as a WebAssembly bundle). Both are kept external to the server bundle (`serverExternalPackages`). The owner should confirm the LGPL dependency is acceptable.
- Decoding a 50 MP HEIC takes roughly 200 MB of memory for the pixels; the Vercel function memory and duration limits apply (provider-cost register unchanged, €0).
- Photo trash labels are the fixed word "Photo"; an album's is its name.
- Rollback: the migration only adds tables and functions and widens four constraints; to undo, drop the S35 objects (the tables hold only photo data) and restore the previous constraints. Database rollbacks are not automatic.
