# ADR 0020: Trash and recovery: database-owned entries, per-item restore and a generic visibility rule

- **Status:** Accepted for S16 within the approved architecture (§36), CLAUDE.md (database access A, authorization C, background processing B, €0 budget) and the spec decisions of 12 October 2026 on trash (placement, central personal and Home trash, parent items with attachments, conflict handling, bulk restore, early permanent deletion, Home file permissions). The defaults below are open to correction by the owner.
- **Date:** 2026-10-15
- **Step:** S16 (brief: `plans/steps/S16-brief.md`). Builds on S15 (stored files that are deleted keep counting and are purged by a job) and S13 (outbox and jobs).

## Context

Individually deleted items and files stay recoverable for 7 days, in a personal trash and one trash per Home, then are removed. Restoring is automatic when safe, asks the person when there is a real conflict, never overwrites active data, and works on one item or a chosen set. Early permanent deletion and "Empty trash" are allowed with explicit confirmation and per-item permission. Deleted files keep counting against the storage allowance until purged. No module that stores deletable records exists yet (tasks arrive in S18, recipes in S24), so this step builds the mechanism and proves it on a reference record type.

## Decision

**One entry per deleted item, owned by the database.** `private.trash_entries` records the owner (a person or a Home), `module`, `item_type`, the id of the deleted record, a title snapshot for the list (cleared when the entry is restored or purged), who deleted it, when, and when it expires (the same `recovery_days` setting S15 uses for files, 7). Only one open entry can exist per item. The table is not reachable through the API; people use security-definer functions that run with their own session and check their rights on every call.

**Modules plug in through three hooks and one call.** A module's own delete function checks that the actor may delete the item, marks it deleted, and calls `private.trash_move`, passing the files attached to that item and to nothing else. Restoring and purging dispatch on `item_type` to `trash_conflict`, `trash_resolve`, `trash_item_restore` and `trash_item_purge`; a module adds one `case` to each. The reference type `private.trash_samples` (soft-delete column, a real uniqueness constraint on a slot among active items, an optional parent, an optional file) shows the shape and is what the tests exercise. It is not reachable through the API.

**Files travel with their parent.** `trash_move` puts exclusively attached files into the existing file trash (`retire_file`: still counted, recoverable) and remembers them in `private.trash_entry_files`. A file another active item still uses is not touched. Restoring brings the file back to `ready` in the same pool without changing its size accounting (a deleted file already counted), so nothing is charged twice. A file that was purged meanwhile is dropped from the restored item and reported (`attachmentsLost`), so no reference is left broken. Purging an entry releases its files through the S15 path (status `purged`, space released, warning reassessed, object queued for removal) unless another active item uses the file.

**Restore is decided per item.** `restore_trash_entries(ids, resolutions)` locks each entry, rechecks that it is still in the trash, still within its window and still visible to the caller, then looks for a real conflict. A conflict is a violated uniqueness or relationship (a slot now held by an active item, a parent that is itself in the trash), never a matching name. The answer per item is `restored`, `needs_resolution` (with the conflict and the choices the person has), `expired`, `not_found` (also for an entry the person may not see, or one already settled) or `failed`. A request that mixes outcomes still succeeds, and the page reports each honestly. A chosen resolution counts only when it answers the conflict that is really there; a second conflict asks again. Repeating a request changes nothing (the second restore finds the entry settled).

**Who sees what.** Personal trash: its owner. Home trash: a current member sees what they deleted themselves; the Owner and Administrators granted `manageHomeSettings` see every entry (engine action `home.trash.viewAll`, SQL `private.can_see_trash_entry`). The per-module permission matrix is open in the spec, so this is the generic rule; a module step may refine it for its own item type. **Owner decision needed:** whether modules should get a fourth per-type hook for restore/purge rights (for example "may still delete tasks"); until then a member who deleted an item keeps the right to restore or purge it while they belong to the Home. The same rule governs listing, restoring and purging, rechecked at execution, so leaving a Home removes the view and the rights at once. An entry the caller may not see is indistinguishable from one that does not exist, in every function and in the HTTP routes (counts, previews and search leak nothing). The visibility function returns false, never null, so a missing term can never read as permission.

**Early deletion.** `purge_trash_entries` and `empty_trash` use the same per-entry check at execution and skip what the caller may not delete, without naming it. The HTTP routes require `confirm: true` in the body; the page shows a dialog stating what is deleted, from which pool, how many items, and that it cannot be recovered through Madeora. "Empty trash" handles up to 200 entries per call. No separate permission exists for permanent deletion (spec: the same Home permission applies to trashing and permanent deletion).

**Locking and races.** Restore, purge and Empty trash lock every requested entry first, in id order, and `trash_move` locks pools in id order, so overlapping batches queue instead of deadlocking. If an active item takes a slot between the conflict check and the restore, the unique violation is turned into `needs_resolution`, not a failure. "Empty trash" takes the moment the page was loaded and touches only entries deleted before it and still within their window; the page offers it only without filters and says when a full batch (200) means more remain.

**The purge job.** `trash_move` enqueues `trash-entry-purge` for the entry's deadline (outbox, ADR 0017). The job asks `purge_expired_trash_entry`, which purges only an entry that is still in the trash and due, and is idempotent; a restored entry is left alone, and one that is not yet due makes the job retry. There is no separate sweeper: the outbox retries the job, and `trash_stats` shows overdue entries for the runbook; add a scheduled sweep if operations show it is needed. Entries past their deadline but not yet purged are hidden from lists and cannot be restored. `trash_stats` reports overdue entries for the runbook.

**Audit.** Moving to the trash, restoring and purging write `private.audit_events` rows (subject `trash_entry`) with ids and the module and item-type names only, never a title.

## Consequences

- Real modules must call `trash_move` from their delete function and add their three `case` branches; the migration comments and the reference type show how. Their own steps decide recurring-item and externally synchronized-item rules and any narrower visibility.
- Whole-account and whole-Home recovery (30 days) is a separate mechanism (S40) and is not touched here.
- Lock order is entry, then pool, then file; no code takes the pool before an entry, so restore, purge and the S15 file jobs cannot deadlock on each other. Concurrent restore/restore and restore/purge are covered by a two-connection test.
- Storage is switched off until the owner provisions R2; the trash works without it because object removal is queued (as in S15) and runs once storage is configured.
